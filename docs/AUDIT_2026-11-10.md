# Audit: the builder, the kits, the preview and the flow (10 Nov 2026)

Written by Claude after reading `main` at `f51dc54` (everything up to PR #79 and #82). The owner asked for a deep sweep of the agent, the builder, the sandbox and the preview, the design skill, React Bits, the 2D and 3D games, security, and the places people get stuck, with the aim of matching Lovable and going past it.

**How to read this.** Section 1 is what this branch changed, with how each change was checked. Section 2 is what was found, by area, with the file to look at. Section 3 is the ranked list of what to do next. Everything marked **UNVERIFIED** was not run with a real model or on the live site: no provider keys were available in this session, the same as earlier sessions.

**The one finding above all the others.** No real model has ever run the eval suite (HANDOFF.md, D70). Every prompt, guide and kit in the builder, including the ones added here, is judged by reading it, not by measuring it. Until `ANTHROPIC_API_KEY` and `DEEPSEEK_API_KEY` are repository secrets and a baseline is committed, "is the output better" has no answer. That is one click of owner work and it is worth more than any single item below.

## 2. Findings

### 2.1 The agent
1. **The builder never sees what it built.** The visual check (`visual-check.ts`) runs in the owner's browser, only on the Sandpack preview, only if the tab is open, asks the cheap model for defects and "never edits files". On the own-build preview (every 3D project, and everyone whose network blocks CodeSandbox) it is skipped. Meanwhile the run check already has a `screenshots` option that returns phone and desktop PNGs on the server, and nothing in production uses it. Lovable's edge is a loop that looks at the page. This is the largest gap. See 3.1.
2. **The cheap model writes every first build and every follow-up; the strong model only fixes** (`TIER_FOR` in `model.ts`, D19). That was chosen for cost before anyone measured quality. Design judgement is where the two models differ most. Worth measuring: strong model for the first build only, cheap for follow-ups.
3. **Stop throws everything away** (`runner.ts`: "this turn's edits were discarded"). Someone who stops at minute three because the direction is wrong loses the three minutes and is still charged. Saving a checkpoint marked "stopped" that they can keep or revert would cost nothing.
4. **Only the system prompt and the context block are cached** (`model.ts`). A fix pass can run 20 tool rounds on the strong model, and each round re-sends the growing conversation after the cached prefix at full price. A cache mark that moves to the last message would cut fix cost. **UNVERIFIED**: check against Anthropic's current caching rules before changing it.
5. **Kit files are guidance, not rules.** "Use them, don't rewrite them" is in each guide, but nothing stops `edit_file` on `src/game/GameCanvas.tsx` or `src/fx/Reveal.tsx`. An edited file also stops receiving fixes (D85). Either protect them like `src/lib/db.ts`, or accept it knowingly.
6. **Guides only load if the model asks.** The 18 guides hold most of the quality rules, and a cheap model that skips `set_plan`'s guides field builds without them. The log already records which guides loaded; the eval suite should score it.
7. **The system prompt named one kit.** "also games (turn on the game-2d kit)" while five kits existed. Fixed here.

### 2.2 Design capability
1. **No motion at all in generated apps** before this branch, despite D7. Fixed here with the motion kit.
2. **React Bits itself should not be vendored into generated apps.** It is MIT with the Commons Clause, which forbids selling a product whose value derives substantially from it, and GoodBuild charges for builds. `src/components/react-bits/BlurText.tsx` on GoodBuild's own landing page is a smaller exposure but the same licence. This is a reading of the licence, not legal advice: **owner to confirm**. The motion kit is original code for this reason.
3. **Every app starts from the same theme**: white, slate, one violet accent, Inter (`template.ts`). The palette question helps on colour. Nothing varied type, shape or layout until the `visual-design` guide added here.
4. **Eight UI primitives** (button, card, input, textarea, label, badge, skeleton, notice). No dialog, tabs, select, dropdown, tooltip, toast, accordion, sheet or avatar. The builder hand-writes these each time, with focus traps and keyboard handling it gets wrong. A `ui` set of ten more accessible primitives is the next design win after motion.
5. **No generated or stock images.** Without an upload, every page is icons and gradients. AI_AGENT.md already lists this as not built.
6. **The landing-page guide and the template briefs don't share a vocabulary.** The guide has six archetypes; the 41 templates have their own briefs. Worth one pass so a template build and a free-form build are held to the same bar.

### 2.3 Games
1. **2D input bugs**: fixed here (section 1).
2. **Nothing made a game feel good**: fixed here with `juice.ts`. Still missing: a sprite or tile-map helper for platformers, and a fixed time step for physics that must be exact.
3. **3D had no input, no pause and no cleanup**: fixed here.
4. **3D was never played by the run check**: fixed here.
5. **Leaderboards trust the player's device.** The guide says so honestly. A signed score (the game's moves replayed on the server) is the real fix and is a large piece of work.
6. **The multiplayer guide is honest that it polls.** Real-time play needs a socket service that does not exist. Not a bug; a product line to decide.
7. **Sound on iOS.** `sound.ts` resumes the audio context on demand, which is right. **UNVERIFIED** on a real iPhone or in MiniPay.

### 2.4 Preview and sandbox
1. **Two Tailwinds**: fixed here by pinning.
2. **No select-to-edit.** AI_AGENT.md §4 designs it (click an element in the preview, attach its file and line to the prompt). It is not built, and it is the feature people name first when they describe Lovable.
3. **The Code tab is read-only and there is no export.** No zip, no GitHub. A person cannot take their code out, and cannot fix a typo without spending a build.
4. **No page switcher** in the preview toolbar for multi-page apps.
5. **The in-memory preview cache is per process** (`preview/cache.ts` says so). A second web instance breaks it. Fine today on one VPS.
6. **The Sandpack preview still depends on CodeSandbox's bundler and jsDelivr.** The fallback to the own build after 20 seconds works. Worth measuring how often it fires, and making the own build the default if that is often.

### 2.5 Security
What was checked and held up:
- **Cross-site writes.** Published apps are same-site with the main site, so SameSite cookies do not protect the API. `proxy.ts` refuses any write whose `Sec-Fetch-Site` or `Origin` is not the main site. Correct.
- **Host isolation.** Generated code is served only from `<slug>.` and `pv-<token>.` hosts, and those hosts can reach nothing but their own files and the data API. The routes repeat the host check.
- **Uploads.** Types are read from the bytes, SVG goes through three passes including DOMPurify, and the public asset route serves with `nosniff` and a sandboxing CSP.
- **Generated code paths.** `pathProblem` keeps the builder out of `package.json`, the wallet layer, the data helpers and the contract modules. The publish bundler refuses any package off the list and any `..` path.
- **The run check's browser** has no secrets, no database and no route out.

What to look at:
1. **Published and preview pages allow `connect-src https: wss:`.** An app needs this for chain RPCs, but it also means generated code can send what a visitor types to any server. The app check refuses a list of hosted backends by name; a list can't be complete. Narrowing `connect-src` to the project's chain RPCs, WalletConnect and GoodBuild's own data API would close it. Check it against real apps first: it will break any app that calls another API on purpose.
2. **Google Fonts.** The design guides tell the builder to add a Google Fonts link, so every visitor's address goes to Google. Self-hosting the dozen fonts the guides name removes that and makes pages faster on slow networks.
3. **The motion kit sets `data-fx` on `<html>`.** A published app could set it itself; all that does is turn its own animations off.
4. **Not re-audited here**: contracts, deploy, credits, sign-in. They were reviewed in D82 and have attack tests.

### 2.6 Flow, and where people get stuck
1. **The chat pulled the reader to the bottom**: fixed here.
2. **Stop loses the work** (2.1.3).
3. **Revert uses the browser's `confirm` box** (`workspace.tsx`), which is off-brand and is suppressed in some in-app browsers. The version list shows 12 and has no way to see more or to preview a version before going back to it.
4. **A failed build offers "Try again" and "Fix it"**, both of which spend credits on the same approach. A third choice, "go back to the last version that worked", is one click people will want.
5. **The first minute.** Plan-first asks questions before anything appears. A template or a recognisable request could show a skeleton of the app straight away. Worth a test with real people before building.
6. **Phones.** The workspace has a chat and preview toggle below `lg`. MiniPay users build on phones. **UNVERIFIED** on a real phone, like most phone paths in HANDOFF.md.
7. **Deploy success points at a Contract tab that doesn't show addresses** (already in HANDOFF.md "M5 gaps", still open).

## 3. What to do next, in order

1. **Run the eval baseline.** Add the two secrets, run Actions → Evals with `update_baseline`, commit it. Then run it again on this branch. Nothing else here can be judged without it.
2. **Let the builder look at its page.** **Built on this branch (D87), off by default.** What is left is to measure it: run the Evals workflow once with `visual_review` and once without, compare the pass rate and the cost per scenario, read what the reviewer reported, and then set `VISUAL_REVIEW=1` on the server.
3. **Measure the strong model on first builds** (challenge to D19). Three eval runs: today's routing, strong for first build only, strong for all builds. Decide on cost per good build, not cost per build.
4. **Select-to-edit.** The own build can stamp `data-gb-src="file:line"` on JSX at build time (esbuild plugin, preview builds only), and the bridge script already talks to the workspace.
5. **Keep partial work on Stop**, and add "back to the last working version" on a failed build.
6. **Ten more UI primitives** as a `ui` kit or in the starter: dialog, sheet, tabs, select, dropdown, tooltip, toast, accordion, avatar, switch. Accessible, token-styled, no package.
7. **Export**: download a zip of the project (files plus a README with how to run it). GitHub later.
8. **Narrow `connect-src`** on published apps, behind a per-project allowance for apps that need another API.
9. **Self-host the fonts** the guides name.
10. **A signed-score path for games**, so a leaderboard with prizes does not need an organiser.

## 4. What is not verified
- The motion kit was run on GoodBuild's own build (the publish bundler), not inside the Sandpack preview. It imports a stylesheet the same way the starter's `main.tsx` does, so it should bundle there; open one landing page in the workspace to confirm.
- No change here was run with a real model. The motion kit's pieces work; whether `deepseek-flash` uses them well, and with restraint, is unknown.
- The `visual-design` guide adds about 5,300 characters to a build that loads it. Its effect on cost and on output is unmeasured.
- WebGL in the production `checker` container. If it has none, Scene3D shows its plain message and the new 3D check reports nothing, which is the old behaviour.
- The chat scroll change and the game canvas sizing were tested by rule and in headless Chromium, not by hand on a phone.
- The Commons Clause reading in 2.2.2 is not legal advice.
