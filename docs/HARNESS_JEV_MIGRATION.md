# Replace keyword routing in the GoodBuild harness

**Start with one shared interpretation of what the person wants.** Today “a game for four players” can trigger multiplayer intake through the player-count rule in `plan-intake.ts:431`, while `delivery.ts:9` can omit the multiplayer milestone for the same words. Conversely, “no wallet” matches the wallet milestone. Adding synonyms in either place leaves the two decisions free to disagree. Jev should give intake, delivery, the builder and the test planner the same answer, including explicit exclusions.

## Integrate TypeSafe AI’s Jev

Use a server-side TypeSafe client for classification. Send the current request, relevant prior goal and explicit intake answers as named state fields to `POST /v1/systemone`, with a bearer API key. Bundle questions that share this state. Select a tested model version available through `GET /v1/models` and record the returned model, question-set version, input revision, answers and usage. The existing writer produces specs, code and open-ended requirements. [TypeSafe API reference](https://api.typesafe.ai/docs)

Ask independent **Noul** questions for capabilities that can occur together. Each returns the probability that its statement is true. For wallet intent, ask separately whether the user wants visitors to connect a wallet and whether they explicitly exclude that interaction. A wallet mentioned as the subject of an article can score low on both. Use **Choice** for a single catalog selection, with a companion Noul asking whether any candidate fits. An unfamiliar request can then proceed to the custom builder. [Noul questions](https://docs.typesafe.ai/primitives/noul.md) · [Companion Noul pattern](https://docs.typesafe.ai/patterns/companion-noul.md)

| Requested signal | Exclusion signal | GoodBuild action |
|---|---|---|
| High | Low | Record a requested capability and resolve eligible kits and checks. |
| Low | High | Record the exclusion and suppress automatic setup for that capability. |
| Low | Low | Carry the original requirement forward. Leave the capability unspecified. |
| Conflicting or borderline | Any unresolved combination | Apply explicit current-turn controls first. If the ambiguity changes scope, ask a focused question. |
| Missing response | Missing response | Record the provider error and follow the existing fallback path. |

Calibrate the high and low thresholds per decision family against labeled GoodBuild requests. During implementation, run the first pilot on multiplayer, wallet and continuation, including negations, quoted examples and requests outside the catalog. Measure classification errors, abstentions, latency and cost before switching traffic. Keep source message IDs and original wording in application state so the builder can recover details that have no predefined label.

## What one decision looks like

For “let four friends draw together in a private room, with no wallet,” the proposed decision records `multiplayer = requested` with a reference to the original message and `wallet = excluded` from the same message’s explicit “no wallet” instruction. It also carries the original drawing requirement, even if the kit catalog has no drawing kit. Intake can ask whether drawing is simultaneous or turn-based. Delivery can schedule shared play. The builder can implement a custom canvas. The verifier can try two independent sessions and check whether the second sees the first person’s mark. If the available room implementation requires wallet sign-in, flag that conflict before selecting it. This is the distinction that lets the catalog grow without turning every new idea into another keyword list.

**Typed button actions (D173, done).** Canned sends carry an `action` id and reuse the saved decision instead of classifying button words. Repairs keep their milestone. The old text match remains only for clients that send no id.

## Implementation order

1. **Freeze a baseline and define the decision.** Label a held-out set of real eval prompts and new paraphrases before tuning. Version the classification schema and catalog. Persist the turn action, goal, capability records (requested, excluded, unclear), source message or answer IDs, optional catalog suggestions and original free-text requirements. Match only known IDs to executable tools. Keep novel requirements as text for the builder and acceptance planner. An unknown capability should still produce a general app through the existing tools.
   Deliver the replay dashboard and pull-request check described below alongside this baseline. Both are required for the first pilot.
2. **Resolve the admission boundary first.** `startTurn` currently holds a project row lock while it creates or extends delivery, before funding admission finishes. Queue an admitted job with its action, source message and project revision. Have the worker classify outside the transaction, then atomically validate the revision, active job and delivery position before applying the result. Preserve immediate busy/stale responses for explicit continuations. Make decision storage and usage accounting idempotent by job, input revision and schema version. A stale result triggers re-evaluation against current state. Check funding before inference and account for any dedicated call.
3. **Share the result through intake and setup.** Persist it alongside the existing job/setup checkpoint (`turn-progress.ts`). Use selected answers and changes in the latest request to refine it once per revision. Explicit exclusions and newer instructions win over a historical mention. Derive questions, milestones, kits and spec routing from the same revision. On provider timeout, malformed output or uncertainty, preserve explicit choices, use a generic local build where possible, or ask one targeted question when scope depends on it. Resume saved setups with their original version. Never reclassify a committed decision on replay.
4. **Move writer and verifier consumers.** Add typed plan-step, viewport and check IDs to existing tool outputs. Use the same requirement IDs from the spec through generation and check results. The test planner can propose checks. The verifier stores independent pass, fail, skipped or unverified results and their evidence. Introduce each structural replacement in the inventory next to its existing check and compare results before removing it.
5. **Roll out by decision family.** Review baseline and candidate results in the replay dashboard for each decision family, then shadow Jev on a bounded sample of new jobs. Record disagreements per capability, explicit exclusions, false milestone advances, unknowns, invalid IDs, per-turn latency, classifier cost, repair counts and verified end-to-end success. Activate intake and delivery together for a cohort, then kit/spec selection, then check selection. Pin behavior to each job. Roll back new admissions to the previous version if a gate fails. Retire the old semantic keyword lists after held-out and live comparisons pass.

## Replay dashboard and pull-request check

**Offline replay dashboard.** Extend the existing eval reporting to generate a local HTML report from versioned, labeled fixtures and saved Jev responses. For each scenario, show the expected decision, the legacy regex result, the candidate decision and the resulting milestone, kit or check. Allow filtering by capability and outcome so a reviewer can find an ignored exclusion even when overall accuracy improves. Record the fixture corpus, model, question set, catalog and threshold versions. Recompute threshold changes from saved probabilities offline. A wording or model change requires fresh responses, collected through the existing opt-in eval workflow in `.github/workflows/evals.yml`. Mark missing or incompatible responses as unevaluated and show their count in the report.

**CI check for new routing regexes.** Add a TypeScript syntax-tree check to the existing PR workflow in `.github/workflows/ci.yml`. Compare the PR head with its merge base and inspect new or changed regex literals, constructors and uses of named patterns in harness routing code, including shared helpers imported by those paths. Report the file, line and decision affected when a pattern interprets a request, plan answer or model reply to choose a milestone, kit or check. A flagged change needs a Jev decision or a narrowly documented exception. Use the inventory as a baseline and keep exact validators, explicit regex search and test assertions eligible. Preserve the workflow’s existing deploy invocation.
