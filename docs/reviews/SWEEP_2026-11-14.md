# GoodBuild security and user-funds sweep (14 Nov 2026)

**Reviewed:** `main` at commit `24dda6d2419d0e04fa20365f73c026ee495b2cab` (read-only; no application code changed).
**Method:** six parallel source reviews (credits and money; auth and compliance; every route's authorization; generated apps and isolation; agent, kits and jobs; deploy, GitHub and infra), then the lead re-read the code behind each finding below. Every finding is labelled with how it was confirmed. Nothing was run against production: no SSH, no wallets, no transactions, no state-changing requests. The local test suite was **not** run (the checkout has no `node_modules`). One reproduction was run in plain Node (GB-09).
**Format:** follows the Daybreak Blue review that produced GB-01 to GB-03 (fixed in D106 to D109). Numbering continues from GB-04.
**Confidence labels used:** *source-confirmed* means the lead re-read the cited lines and the described behaviour follows from them; *source-reported* means a sub-reviewer read the code and the lead re-read only part of it; *plausible* means it depends on behaviour (a node, a browser, a provider) that was not observed. None is dynamically reproduced unless it says so.

---

## Verdict

No way was found for an ordinary signed-in user to take credit they did not pay for, to read or write another user's project, or to reach another app's data. Authorization on all 53 routes is consistent (session, then ownership), the credits ledger and contract are carefully built, and the D106 to D109 fixes held up against the attacks tried, with the exceptions in GB-04, GB-05 and GB-15, which are gaps in the fixes themselves. The findings that matter most are in the **mainnet exploit-test gate** (GB-04, GB-05): it can record "passed" when no test ran, and it misses several ways of holding money, so it is weaker evidence than the UI and `deploy_reviews` suggest. Next is **one hot key deciding how much credit exists** (GB-06), **cost and compliance rules that rest on a client flag or on model obedience** (GB-07, GB-08), and **two ways a signed-in user can stall the shared server** (GB-09, GB-10). Most of the rest is Low: recovery problems, copy that promises more than the code, and doc drift. Nothing here is a confirmed loss of user funds.

## Findings, ranked

### GB-04. Medium. The mainnet exploit gate can record "passed" when no exploit test ran (D107, pattern: heuristic gate)
*Confidence: source-confirmed; not dynamically reproduced.*

- **Where:**
  - `src/server/agent/kits/dao-vault.ts:71` collects exploit tests with `/function\s+(testExploit\w*)\s*\(\s*\)/g` over raw file text, for any file matching `^contracts/.*\.t\.sol$`.
  - `src/server/agent/kits/dao-vault.ts:94,100`: "asserts something" is a regex for `assert*(` or `expectRevert*(` in the body; a need is met by matching the function **name** only.
  - `src/server/agent/checks.ts:475,529`: only files under `contracts/test/` are treated as tests and compiled as such (`isTestFile`).
  - `src/server/agent/contract-tests.ts:25`: no compiled tests means `{ results: [], issues: [] }`, which is "no problem".
  - `src/server/deploy/exploit-gate.ts:47`: with no issues, the gate returns `exploitTests: "passed"` unconditionally.
- **Flow:** a project holds money. The builder, chasing the check, writes `testExploitReentrancy` and `testExploitUnauthorizedCall` in a comment, in `contracts/Pool.t.sol` (outside `contracts/test/`, so never executed), as a non-public function, or with `assertTrue(true, "")`. One function name such as `testExploitUnauthorizedReentrancyDonation` satisfies several needs at once. The gate passes, `deploy_reviews.exploitTests` records `passed`, and the deploy modal says the tests pass.
- **Who is affected:** depositors in vaults, DAOs and any custody contract on Celo mainnet; the owner who reads "passed". The author is realistically the AI chasing a check, not an attacker.
- **Preconditions:** a money-holding project deployed to mainnet. Not theft by GoodBuild; it is an audit-trail and assurance problem. D107, the guide and the FAQ already say the tests are "not an audit", which limits the damage.
- **Smallest fix:** strip comments and strings before matching; require `public`/`external`; and record `passed` only if each required test name appears in the **executed** results with `ok`. Zero executed tests with custody present should be a refusal, not a pass.
- **Test that would verify it:** a gate test with (a) a commented-out `testExploitReentrancy`, (b) the same function in `contracts/Pool.t.sol`, (c) `assertTrue(true)` only: each must refuse. `gb02.test.ts` and `kits/dao-vault.test.ts` cover only missing tests and present-but-assert-free tests; neither covers these.
- **Related (same root, also source-confirmed):** `rolesOf` (`dao-vault.ts:25-28`) decides `knownShape` by regex on raw source including comments. `service.ts:146` skips the owner-review step when `knownShape` is true. A custody contract with a comment containing `function deposit(` and `function withdraw(` becomes "a vault" and never gets `needs_owner_review`. `gb02.test.ts` proves `custodyOf` ignores comments; nothing tests `rolesOf` with comments.

### GB-05. Medium. `custodyOf` still misses several ways to hold other people's money (D107 gap)
*Confidence: source-confirmed for the code limits (`custody.ts:64-75` re-read); the specific bypass contracts were not compiled, so each is plausible.*

- **Where:** `src/server/agent/custody.ts:64` only inspects `contractKind === "contract"`; `:67-70` names only `ERC4626*` and `Governor*` bases; `:71-75` looks at `FunctionDefinition` only and skips constructors; the `HOOKS` set lacks ERC-1363 `onTransferReceived` / `onApprovalReceived`.
- **Not flagged:** (a) a `library` or file-level function doing `token.transferFrom(from, address(this), a)`, inlined into a contract whose own functions have innocuous names; (b) a constructor that pulls tokens (a factory deploying `new Escrow(buyer, amt)`); (c) contracts that inherit receivers from OpenZeppelin (`ERC721Holder`, `ERC1155Holder`, `TimelockController`, `VestingWallet`), because only files under `contracts/` are analysed; (d) bases imported under an alias (`import {ERC4626 as Base}`); (e) `Address.functionCall(...)` pulling tokens (the guardrail blocks `functionDelegateCall` but nothing in `checks.ts` mentions `functionCall`); (f) plain `token.transfer()` funding followed by payout of `balanceOf(address(this))`, arguably "own money" in some designs.
- **Held up (reviewer-reported):** keyword-in-comment tricks, unicode identifiers, payable functions, `receive`, payable fallback, `.call` with data, assembly, `delegatecall`, `selfdestruct`.
- **Flow and who:** the gate returns `not_required` and the deploy proceeds to mainnet with no named tests and no owner review; the same as GB-02 but through shapes D107 did not list.
- **Smallest fix:** scan libraries, free functions, constructors and modifiers; resolve bases through the inheritance graph rather than the written name; add OZ holder bases and the ERC-1363 hooks; or decide custody from the compiled ABI (payable functions, `receive`, `onERC*Received`). Add `functionCall*` to the guardrail.
- **Test that would verify it:** one `custodyOf` case per bullet above. The existing cases cover only the shapes in the D107 list.

### GB-06. Medium (conditional). One hot key and one owner key decide how much credit exists, and the server credits any `Redeemed` event without matching it to a quote
*Confidence: source-confirmed (`onchain.ts:78-89,117-126`, `GoodBuildCredits.sol:118-148` read by the lead); not dynamically reproduced.*

- **Where:** `src/server/credits/onchain.ts:78-89`: `recordRedemption` inserts the event, calls `markQuotePaid` only if a ref is present, then posts a ledger deposit. `credit_quotes` is never used to refuse anything: an event with an unknown ref is credited in full; nothing compares the credited amount to the quote's `creditsMicro + bonusMicro`, or `gdPaid` to `gdWei`. `contracts/GoodBuildCredits.sol:118-129` accepts any quote signed by `quoteSigner`; `grant` (`:140-148`) is owner-only, capped per call by `maxPerQuote` but with no cumulative cap; `setMaxPerQuote` has no upper bound.
- **Flow:** whoever obtains `CREDITS_QUOTE_SIGNER_KEY` (it sits in `.env.production` and in the `web` and `worker` containers, `deploy/docker-compose.yml:55`) signs quotes for `gdAmount = 1` and `credits = maxPerQuote`. The contract accepts them; the scanner credits them within about a minute. The same follows from a compromised owner key via `grant`. `pause` does not stop `grant`.
- **Who is affected:** the platform (credits spendable against real model cost); not other users' balances directly.
- **Preconditions:** theft of the signer or owner key, or a malicious operator. Trust assumption, not an exploit by users.
- **Smallest fix:** in `creditRow`, post a deposit only if the ref matches a `credit_quotes` row for the same wallet and amount; otherwise hold it for review (an explicit allow-list for owner grants and the launch purchase). Add a per-wallet and global daily deposit velocity alert.
- **Test that would verify it:** a `onchain.test.ts` case "`Redeemed` with an unknown ref, or an amount that differs from the quote, is recorded but not credited". The existing tests (`onchain.test.ts`, `credits-contract.test.ts`) cover the happy path and the contract's own checks.
- **Trust assumptions to state in docs:** the owner can withdraw all G$, release up to the remaining supply with `grant`, replace the signer, raise `maxPerQuote` without bound, and pause sales. G$ is assumed to have no transfer fee (the contract does not check the balance change after `safeTransferFrom`; UNVERIFIED). Whether the owner is a multisig cannot be told from the repo (`docs/CREDITS.md:36` says Safe; `DEPLOY.md` says "admin wallet").

### GB-07. Medium (cost abuse, not theft). Magic is not required for email sign-ins, and the free allowance is per wallet with no rate limit on sign-in
*Confidence: source-confirmed (`verify/route.ts:32`, `api-schemas.ts:10`, `cap.ts:7-15` re-read).*

- **Where:** `src/app/api/auth/verify/route.ts:32` runs `assertMagicLogin` only `if (body.walletKind === "embedded")`, and `walletKind` is a client-supplied field (`src/lib/api-schemas.ts:10`). Sending `"external"` with a SIWE signature from a fresh throwaway key skips Magic entirely. `src/server/credits/cap.ts:7-8` says "Magic gives each email one wallet, so this also caps each email"; that is not true in code. Each new wallet gets `UNVERIFIED_CAP_MICRO` ($0.20, `cap.ts:15`). No rate limiting was found on `/api/auth/*` (the only limiters are in `model.ts`, app-data and support).
- **Flow:** a script generates keys, calls nonce then verify with `attestation` true, and builds on free credit. The only brake is the global `FREE_BUDGET_MICRO` ($4) with $0.35 held back per running build. Scripted accounts can exhaust the trial for real users ("The free trial is full right now").
- **Who:** the free-trial budget and legitimate new users (availability), up to $4 of provider spend. Known and accepted for a single wallet (D28); the point is that the Magic gate does not do what the comment says.
- **Smallest fix:** per-IP rate limit on nonce and verify (the firewall is Cloudflare-only, so `cf-connecting-ip` is usable); correct the `cap.ts` comment; make the free tier require Magic or GoodID.
- **Test that would verify it:** post `walletKind: "external"` with a fresh key and expect the free allowance to be refused (or the rate limit to trip). `magic.test.ts` and `service.test.ts` only test `assertMagicLogin` when it is called.

### GB-08. Medium (compliance). The "no sports betting" rule exists only as prompt text; the building model is the cheap one
*Confidence: source-confirmed that it is prompt-only (reviewer grep of `src/server` and `src/lib`; lead re-read the `skipPlan`, `confirmed` and attestation points); how often the model complies is UNVERIFIED (no live eval baseline, D70).*

- **Where:** the refusal appears at `src/server/agent/plan-intake.ts:192` and `src/server/agent/prompt.ts:181` (and a kit note). There is no input classifier, no output check, and no deploy or publish gate for betting or games of chance. `skipPlan` is a client boolean (`src/components/workspace/use-workspace.ts:19-20,134`) that skips the intake refusal; the publish confirmation is only `confirmed: z.literal(true)` (`src/app/api/projects/[id]/publish/route.ts:14`) and is not persisted.
- **Bypass:** rephrase ("prediction market", "pool members stake on a match result, owner settles", "raffle"); a prize pool "skill" game is explicitly allowed by the prompt; a design-reference image can carry the spec into the builder context. A pooled-stake contract is classified by `rolesOf` as a vault, so it needs only the generic exploit tests.
- **Also not code-enforced:** nothing prohibits an `onlyOwner` function that withdraws user deposits; the access test only checks a stranger cannot call it. A deliberate rug-pull passes every gate; only the prompt and the "Unaudited contract" label stand in the way.
- **Smallest fix:** a deterministic keyword pre-check plus a short classifier call on the request and on contract text, recorded on the turn and enforced at publish and deploy; persist the publish attestation with its text version; at minimum, say in the docs that this is best-effort. Add owner-withdraw detection to custody.
- **Test that would verify it:** run the "sports betting" and reworded prompts through the planner in the eval suite (`refuse-betting` is one plain-wording prompt, run on demand); `plan-first.test.ts` only checks the prompt text.

### GB-09. Medium (conditional). The agent's `search_code` regex runs unbounded in the worker process
*Confidence: source-confirmed (`codebase.ts:164-176` re-read). The regex hang was reproduced in plain Node (`/(a+)+$/i` against 30 `a`s then `!` did not finish within a 10 s timeout); not run inside the worker.*

- **Where:** `src/server/agent/codebase.ts:164` builds `new RegExp(query, …)` when `regex` is true, and `:176` runs `re.test(line)` over every line of every file, with no timeout or engine limit.
- **Flow:** a project owner asks the builder to "search with regex `(a+)+$`" and has it create a file with a line of `aaaa…!`. The worker's event loop blocks, so it stops renewing leases for other users' builds (`TURN_CONCURRENCY` builds share the process). After lease expiry the job is re-claimed and may hang again, up to the attempt limit.
- **Who:** every user whose build runs on that worker; the attacker needs only an account with an AI allowance.
- **Smallest fix:** use a linear-time engine (RE2) or run the search in a worker thread or child process with a timeout; at minimum cap pattern and line length and reject nested quantifiers.
- **Test that would verify it:** a test that `searchCode` with `(a+)+$` on a 40-character line returns within a time bound. `codebase.test.ts` covers only an invalid regex.

### GB-10. Medium (conditional). Expensive routes have no concurrency limit or rate limit: compile, exploit-gate tests, uploads, visual checks
*Confidence: source-reported (the lead confirmed the child-process call at `checks.ts:171` and the absence of a limiter in the compile path; the per-route counts are the reviewers').*

- **Where:** `src/server/agent/checks.ts:171` spawns a `solc` child (`maxBuffer` 64 MB) per call. It is reached from deploy/prepare (which also runs the exploit tests), preview, publish and the deployment record (which recompiles). Uploads (`assets/route.ts:34-39`) and `visual-check` (`:27-35`) call the model after `checkAiAllowance` only, and parse or buffer the whole body before the size check (a chunked body reports length 0). `decideDirectFunding` (`cap.ts:203-212`) deliberately lets simultaneous direct calls pass.
- **Flow:** any account (a wallet is enough) fires parallel POSTs. The production plan is one small VPS (D27), so CPU and memory saturate for everyone. Cost overshoot is N times one vision call.
- **Smallest fix:** a global compile semaphore (for example 2) with a queue, a per-user in-flight limit on these routes, and size limits applied while streaming the body.
- **Test that would verify it:** a concurrency test on prepare and on upload. `gb02.test.ts` and `mainnet-switch.test.ts` cover gating, not concurrency.

### GB-11. Low to Medium (reliability, affects every user after 24 hours). Session rotation in a Server Component revokes the old session but cannot set the new cookie
*Confidence: source-confirmed on the code path (`service.ts:104-107`, `http.ts:52-58` re-read); not run against Next. Whether `cookies().set` throws in Server Components on this Next version is what the code's own `try/catch` assumes.*

- **Where:** `resolveSession` revokes the row and issues a new one when the session is older than 24 hours (`src/server/auth/service.ts:104-107`). `currentSession` calls `setSessionCookie` inside `try { } catch { // the next route handler call rotates it }` (`src/server/auth/http.ts:52-58`). The comment is wrong: the old row is already revoked and the browser still holds the old token, so the next request finds nothing (`service.ts:98` filters `isNull(revokedAt)`).
- **Flow:** the first request after 24 hours is a Server Component page (`src/app/p/[id]/page.tsx:23`, `src/server/home-data.ts:12`): the user is signed out. Concurrent requests with the same old cookie behave the same way.
- **Smallest fix:** rotate only in route handlers, or keep the old row valid for a short grace period, or revoke only after the cookie was set.
- **Test that would verify it:** `service.test.ts` has no case for "rotated but the cookie write failed" or for two concurrent resolves.

### GB-12. Low to Medium. Interrupted or crashed model calls are never billed, so the free cap and global budget can be bypassed
*Confidence: source-confirmed (the `runner.ts:316-330` comment says an unfinished call "is not billed"); the provider-cost size is conditional on tier.*

- **Where:** `src/server/agent/runner.ts:322-326` commits usage only after the stream completes; stop aborts the controller, so nothing is recorded. `spentMicro` and `budgetHasRoom` (`cap.ts:89,127`) sum only recorded `usage_events`.
- **Flow:** a free account starts a build, stops it once generation begins, and repeats. The provider bills the input tokens and the output generated so far. The build tier is DeepSeek, so it is cents per cycle; review and fix calls use the strong tier and cost more. Paid users are also not charged for an aborted call (a loss to the platform).
- **Smallest fix:** on abort or error, record an estimated usage row (measured input tokens plus output received), or cap started calls per user.
- **Test that would verify it:** a stop test in `runner.test.ts` that asserts a usage row exists; the current stop tests assert only that edits are discarded.
- **Related, Low:** `RESERVED_PER_BUILD_MICRO` is $0.35 (`cap.ts:36`) while the free build ceiling is $1 with a hard stop at 2x (`runner.ts:105,248`), so a few concurrent free builds can exceed the $4 global budget.

### GB-13. Low (recovery problem, not theft). Credit scanner and ledger: key on log index, no confirmation depth, cursor trusts one view of the chain
*Confidence: source-confirmed for the code (`onchain.ts:52,115-117,168-187` re-read, and a grep for `confirmations`/`blockTag`/`finalized` finds nothing); the reorg and lagging-node behaviours are plausible (not observed).*

- **Where:** the ledger key is `onchain:<chain>:<tx>:<logIndex>` (`onchain.ts:52`). The redeem route credits straight from the receipt (`:115-117`); the scanner reads up to `head` (`:168`) and advances the cursor to `to` (`:187`). `creditsClient` uses a fallback transport (`chain-client.ts:176-181`), so `getBlockNumber` and `getContractEvents` can be answered by different nodes.
- **Failure modes:** (a) a reorg re-includes the same transaction with a different `logIndex`: a different key, so the same burn is credited twice, and the 64-block re-read overlap picks up the second copy; (b) the transaction is dropped after crediting: the credit stands but the G$ never moved and the quote's `used[ref]` is still false, so it can be paid again; (c) a node serving logs lags behind `head` by more than the overlap: the cursor skips those events silently. Recovery for (c) is the user's own redeem, the "Missing a payment?" form, or `scripts/credits-reconcile.ts` (which reports but does not heal).
- **Docs promise more:** `docs/CREDITS.md:40` says "wait N=3 blocks"; the code has no confirmation depth. The comment "Re-reading is free: events credit once" does not hold for (a).
- **Smallest fix:** key the ledger on `onchain:<chainId>:<ref>` (the contract guarantees one `Redeemed` per ref), scan and redeem only at depth N or the `safe` tag, and advance the cursor to `head - K` (K of about 128).
- **Test that would verify it:** record the same tx and ref with a different `logIndex` and expect one ledger entry; a short `getContractEvents` result and the cursor stopping at `head - K`. `onchain.test.ts` has neither.
- **Hardening:** `Number(l.args.credits)` (`:183`) is outside the try, so one poison log would stall the cursor; unreachable with the real contract's supply. The scanner runs only in the Node server process (`instrumentation.ts:10`); with `BACKEND_ORIGIN` set or on a serverless host it does not run. If `CREDITS_START_BLOCK_<chain>` is unset the first scan starts at block 0.

### GB-14. Low. The monthly GoodID bonus cap is check-then-act
*Confidence: source-confirmed (`quote.ts:96-106,161-175` re-read); financial leakage is bounded.*

- **Where:** `bonusRoom` is read at `src/server/credits/quote.ts:161-162` and the quote inserted at `:175`, with no transaction, lock or unique constraint, and no rate limit on the route. Parallel quote requests each see the full room.
- **Impact:** only the cap is bypassed; the bonus is still 10% of what is paid and each quote is redeemable once. A second window: an unpaid quote counts toward `bonusRoom` only while `deadline > now`, and `paidAt` is set only when the scanner or browser sees the event.
- **Smallest fix:** `pg_advisory_xact_lock(hashtext(root))` around the read and the insert; count unpaid quotes for a short grace period after the deadline.
- **Test:** a `Promise.all` of three `issueQuote` calls on one root; `quote.test.ts` is sequential. (The free-AI allowance across accounts sharing one GoodID root has the same shape: `cap.ts:155-157,194`, at most one build, about $0.35, per account over the cap, bounded by the global budget.)

### GB-15. Low (conditional, recovery problem). A deploy reconciler stale read can lead to a second deploy (D108)
*Confidence: plausible (code read by the sub-reviewer; the stale-node behaviour is described in the repo's own comments in `upgradeable.ts:70-75`, not observed).*

- **Where:** `src/lib/deploy/reconcile.ts:36-54` makes three separate reads against the public RPC. If one node answers "no receipt, tx unknown" and another `getTransactionCount(latest) > nonce`, the transaction is classed `replaced`, and a stale `getCode` returns `0x`, giving the "can send again" path (`run.ts:280-283`). The first transaction may have mined, so a second contract and second fee follow. `use-deploy.ts:157-160` stores the nonce as `seen ?? next`, where `next` is the pending count read before the wallet prompt; a wrong guess can misclassify "dropped" versus "replaced".
- **Smallest fix:** before treating `replaced` or `dropped` as safe, re-read after a wait or from two clients and require agreement; derive the nonce from `getTransaction` with retry and do not persist a guess.
- **Test:** `reconcile.test.ts` has no mixed-node-answer case.
- **Related Low:** the owner-review checkbox is kept after a rebuild and re-prepare (`use-deploy.ts:82,207`), and the server stores only the boolean and time, not which custody list was shown (`service.ts:163`); recorded constructor arguments are not checked against the manifest (`service.ts:402-422`), so "reviewed" covers code, not parameters.

### GB-16. Low to Medium. Generated-app isolation and takedown gaps
*Confidence: source-confirmed for the takedown script, preview and rename points (lead re-read); the browser-behaviour items are plausible.*

1. **Takedown purge leaves visitor emails, and the docs say it removes them.** `scripts/takedown.mjs:17-22` deletes records, usage, sessions and nonces only, not `app_data_email_codes` or `app_data_email_identities`. `docs/APP_DATA.md:40` says a takedown purge removes "the address, its codes and its sessions". `deleteProjectData` (`store.ts:445-453`) does clear them; the script does not call it. The test at `email.attack.test.ts:351` calls `deleteProjectData`, not the script. Fix: call `deleteProjectData` or add the two deletes.
2. **Takedown does not cover the preview host.** `buildPreview` (`src/server/preview/service.ts:56-80`) never checks `publications.disabledAt`, and neither does the preview route; a taken-down owner can keep serving the app at `pv-<token>.<domain>`, which has no GoodBuild bar, Report link or "Unaudited contract" label. Fix: refuse preview builds and serving for a disabled publication.
3. **A slug released by renaming is claimable at once** (`publish/service.ts:151-155`, `slugAvailable`), although the schema comment says the slug stays with the project. Data and sessions are keyed by project, but the old browser origin keeps its localStorage and any wallet "connected site" approval. Fix: a slug-history table that reserves a released slug for its previous project.
4. **The D109 bar is not tamper-proof against the app's own code** (`build.ts:287`): generated JS or CSS can remove or hide `[data-goodbuild-bar]`, and `hasOwnContracts` (`build.ts:231`) needs a `contracts/**/*.sol`, so an app that calls a hard-coded external contract gets no label. "The owner can't turn it off" is true of the setting, not of the code.
5. **Same-site cookie bombing** (plausible): apps run on `<slug>.<domain>`, and `__Host-` cookies stop overwriting the session but not `document.cookie = "x…; Domain=<apex>"` floods that push main-site requests over header limits. A separate registrable domain, or the apps domain on the Public Suffix List, closes it.
6. **Brand-word slugs** (`published-host.ts:10-14`): reserved names are exact-match, so `goodbuild-support` or `gooddollar-claim` is a valid slug on the official domain.
7. **Upload quotas race** (`asset-store.ts:132-139`): list, check, then insert, with no lock, so parallel uploads exceed 20 files or 25 MB; no per-account byte cap.
8. **Rate-limiter reset** (`app-data/limits.ts:80-82`) clears all in-memory counters at 50,000 keys, and anonymous writes create a fresh key per request. The database-based email caps survive.
- **Still open from `docs/AUDIT_2026-11-10.md` §2.5:** `connect-src 'self' https: wss:` (`publish/service.ts:205`, same in preview headers), so generated code can send what a visitor types to any server; and the design guide still tells the builder to add a Google Fonts link (`guides.ts:144`). Also no Permissions-Policy on app pages. The `HOSTED_BACKENDS` name list (`checks.ts:647`) is the only exfiltration guard.

### GB-17. Low to Medium. App email sign-in: a send timeout is un-counted, and one app can drain the site-wide cap
*Confidence: source-reported for the timeout (plausible, depends on Resend latency); the cap structure is source-confirmed against `limits.ts:44-47` (cited by two reviewers).*

- **Timeout (pattern b):** `email.ts:157` aborts the Resend call after 10 s; `requestEmailCode` (`:230-236`) then deletes the code row, and every daily cap is counted from that table. A send Resend actually accepted does not count, so only the per-minute in-memory limits remain. Fix: delete the row only on a definite refusal.
- **Shared pool:** the site cap is 90 codes a day across all apps (`email.ts:119-121`), while one app may use 100 and one IP 20. Publishing one email-enabled app and sending from about five IPs makes `email_site_cap` trip for every app for a day; the sender is the official address and the visible host is the attacker-chosen slug, so it can also mail-bomb a chosen address. `APP_DATA.md:39` admits Turnstile is not built but not the site-wide effect. Fix: a per-app share of the site budget, a lower per-IP site cap, Turnstile.
- **Test:** `email.attack.test.ts:194,214` cover a clean failure and that the cap exists, not a timeout after acceptance or one app exhausting the site cap.
- **Per-IP limits** trust `cf-connecting-ip` then `x-forwarded-for` (`support/route.ts:10`, `app-data/handler.ts:121`). That is sound only while the origin accepts Cloudflare alone (see GB-19).

### GB-18. Low. Hackathon grants: testnet deploy unlocks credits, unbounded refusal log, expiry can stick
*Confidence: source-confirmed for the testnet point (lead re-read `claim.ts:27,155-170` and `register-steps.tsx:115`); the other two are source-reported.*

## Controls observed and remaining trust boundaries

**Held up, with where:**
- **Route authorization:** all 53 `route.ts` files walked. Project routes use `requireSession()` then `getOwnedProject` (`src/server/projects.ts:67-81`); job and deployment ids are tied to the project in the path (`turns/[jobId]/events:30`, `stop:20`, `verify:21`); the deployments route overrides `projectId`, `userId` and `wallet` from the session. No IDOR or mass assignment found. `mainnet` PUT, `hackathon/expire` and the admin page gate on `ADMIN_WALLETS`, parsed and lowercased (`mainnet-access.ts:36-47`), compared only to the SIWE wallet. `support/inbound` fails closed with no secret and uses an HMAC with a 5-minute window. GitHub OAuth state is bound to the user and a signed cookie, with an open-redirect guard (`oauth.ts:159,204-213`). `/api/dev/test-gd` returns 404 in production.
- **Sign-in and cookies:** SIWE order of checks (nonce, domain from `APP_DOMAIN` never `Host`, chain allow-list, 10-minute issued-at window, ecrecover); HS256 with separate audiences; DB-backed sessions revoked on logout; `__Host-` cookies; cross-site writes refused by `Sec-Fetch-Site`/`Origin` on every `/api` path (`proxy.ts:17-28,94`); edge secret compared in constant time (`edge.ts:13-18`).
- **Credits:** ledger validation, balance lock, idempotency with replay assertions, overflow and negative guards (`ledger.ts:138-180`); the event row is locked and the ledger entry posted in one transaction, so scanner and browser redeem credit once (`onchain.ts:62-63`); amounts and wallet come from the log, not the caller; quote amounts, chain, root and price are server-side; the contract's quote hash covers buyer, credits, bonus, ref and deadline with a chain-bound EIP-712 domain, `used[ref]` is set before release, `ReentrancyGuard`, non-transferable credits, `Ownable2Step` with renounce disabled, and `withdraw` cannot take the credit token. Paid builds lock job then balance in a fixed order.
- **Deploy:** `recordDeployment` takes address, sender and args from the receipt and checks `tx.to === null`, `tx.from === wallet` and a bytecode prefix (`service.ts:368-404`); unique `(chain, tx)` and `(chain, address)`; the upgradeable path is testnet-only on the server in three places (`upgradeable.ts:43`, `service.ts:138,355-358`); the mainnet record path needs a `deploy_reviews` row or runs the gate itself (`service.ts:379-398`); only two `insert(deployments)` sites exist; test files never deploy and deploy-time guardrails re-run on every chain.

- **Agent layer:** the workspace is an in-memory map, so no filesystem traversal; `pathProblem` blocks `..`, absolute paths and platform files; no server-side fetch of a user-supplied URL was found (SSRF); prompt injection reaches only the user's own files. No OpenRouter reference exists in `src`; no route exposes model output or a proxy publicly.
- **Infra:** `DOCKER-USER` rules restrict ports 80/443 to Cloudflare ranges; `deploy.yml` passes no secrets to the checks job, writes the SSH key with `umask 077`, pins the host key and deletes the key `if: always()`; no secrets in tracked files; `NEXT_PUBLIC_*` values are non-secret.
